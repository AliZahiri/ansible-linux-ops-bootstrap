# v0.3.0 — SSH Key and Systemd Safety Contracts

Status: published as `v0.3.0` on 2026-11-08. This document records the release
notes and publication validation.

## Release intent

`v0.3.0` extends the offline Linux operations checks with stronger contracts
for systemd service execution and SSH authorized keys. CI also validates the
sample playbooks on Ubuntu 26.04 with restricted permissions and pinned GitHub
Actions dependencies.

## Proposed highlights

- Systemd evidence checks cover service hardening settings, runtime identity,
  and capability bounding.
- SSH authorized-key checks cover provenance, expiry, restrictions, and
  permitted source addresses.
- New validators have focused tests and examples and do not connect to hosts or
  require production credentials.
- The Ansible syntax workflow checks the sample playbooks on Ubuntu 26.04;
  GitHub Actions are pinned by commit SHA and the validation workflow uses
  read-only repository permissions.

## Compatibility and upgrade notes

- Existing `playbooks/bootstrap.yml`, `playbooks/monitoring.yml`, and
  `playbooks/backup.yml` remain supported.
- The new validators are additive. SSH hardening remains opt-in and requires
  the existing allowed-user and authorized-key safeguards.
- No production inventory, persisted state, or secret migration is performed.

## Known limitations

- Offline validation checks supplied configuration and evidence; it cannot
  establish that a remote host is running the stated systemd or SSH policy.
- Ansible syntax checks do not connect to hosts or execute playbooks.
- Authorized-key provenance and expiry checks depend on trustworthy input
  evidence and do not revoke a key on a host.
- The example roles remain a baseline and are not a complete CIS implementation
  or environment-specific threat model.

## Rollback

This release adds validators and CI safeguards without changing production
inventories or executing tasks on hosts. If an environment cannot adopt the
new checks, pin its workflow to `v0.2.0` while the policy integration is
reviewed. Do not bypass a failed SSH lockout-safety or recovery control to
complete a host change.
