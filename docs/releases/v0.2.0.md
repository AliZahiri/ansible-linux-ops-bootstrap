# v0.2.0 — Linux Operations Evidence Controls

Status: release candidate. Publication has not been approved. This document is
the source for the GitHub Release notes.

## Release intent

`v0.2.0` evolves the initial Ansible bootstrap kit into a testable operations
baseline. It adds deterministic, offline checks around hardening, backup
recovery evidence, inventory contracts, and operational change control while
keeping the existing playbook entry points and sample-inventory workflow.

## Highlights

- Backup evidence checks cover freshness, encryption, manifests, retention,
  recovery-point diversity, restore execution, checksums, and immutability.
- Linux hardening checks cover SSH authentication and cryptographic policy,
  host-key evidence, firewall drift, audit logging, file integrity, DNS health,
  package-manager locks, kernel settings, and systemd safety.
- Ansible checks cover inventory inputs, collection version locks, role
  dependencies, handler notifications, privilege escalation, change scope,
  check-mode budgets, and sensitive-file contracts.
- SSH hardening is lockout-safe by default: it is opt-in and requires an
  explicit allowed-user contract plus a non-empty authorized-keys file.
- The unit suite exercises the controls without connecting to production hosts
  or requiring production credentials.

## Compatibility and upgrade notes

- Existing `playbooks/bootstrap.yml`, `playbooks/monitoring.yml`, and
  `playbooks/backup.yml` remain supported.
- The sample inventory and example vault variables remain non-sensitive
  documentation fixtures; copy them into a separate environment-specific
  inventory before use.
- No persisted data or production inventory is migrated by this release.

## Known limitations

- Offline validators assess supplied configuration and evidence. They cannot
  prove that a remote host, backup store, collector, or operator-provided
  observation is trustworthy.
- Ansible syntax checks do not connect to hosts or execute tasks.
- Restore evidence controls do not replace a scheduled live restore drill.
- The example roles are a baseline, not a complete CIS implementation or a
  substitute for an environment-specific threat model.

## Release validation

Run from a clean checkout of the candidate commit:

```bash
PYTHONDONTWRITEBYTECODE=1 python3 -m unittest discover -s tests
python3 -m pip install --disable-pip-version-check "ansible-core>=2.18,<2.19"
ansible-galaxy collection install -r requirements.yml
for playbook in playbooks/bootstrap.yml playbooks/monitoring.yml playbooks/backup.yml; do
  ansible-playbook --syntax-check -i inventories/sample/hosts.ini "$playbook"
done
python3 scripts/validate_handler_notifications.py examples/handler-contract.example.json
PYTHONDONTWRITEBYTECODE=1 python3 .github/scripts/daily_pr.py --dry-run
python3 -m json.tool .github/daily-pr/backlog.json >/dev/null
git diff --check v0.1.0...HEAD
```

Expected results:

- all Python tests pass;
- all three playbooks pass syntax validation against the sample inventory;
- the handler contract example is accepted;
- completed automation backlog returns a successful no-op;
- backlog JSON parses successfully; and
- the release diff contains no whitespace errors.

## Rollback

This release adds validation and hardening controls but performs no production
migration. If a downstream environment cannot adopt `v0.2.0`, pin the
repository to `v0.1.0` and retain the previous playbook workflow while the
compatibility issue is investigated. Do not bypass a failed lockout-safety or
recovery-evidence control merely to complete a deployment.
